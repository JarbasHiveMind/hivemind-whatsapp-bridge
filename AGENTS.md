# AGENTS.md — `hivemind-whatsapp-bridge`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

Bridges WhatsApp to a HiveMind node using Meta's WhatsApp Business Cloud API: a
HiveMind bridge is a satellite whose input and output are a chat platform
instead of a microphone. Inbound WhatsApp text messages become
`recognizer_loop:utterance` bus messages; the hub's `speak` replies are posted
back to the originating number via the Graph API. Part of the
[HiveMind](https://github.com/JarbasHiveMind) ecosystem — a protocol for
connecting satellite devices to a hub running
[OpenVoiceOS](https://github.com/OpenVoiceOS). The hub is
[HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core); the client
library is
[hivemind-bus-client](https://github.com/JarbasHiveMind/hivemind-bus-client).
Sibling bridges with the same shape: `hivemind-telegram-bridge`,
`HiveMind_mattermost_bridge`, and the Twilio bridge this one is modeled
after — check them for prior art before inventing a new pattern here.

## Layout / build / test

- Package module: `hivemind_whatsapp_bridge/`. Tests live in `tests/` (check
  before adding — do not create a second test directory).
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[test]" --prerelease=allow`
- Run the suite in the foreground: `python3 -m pytest tests/ -q`. It mocks
  both the outbound HTTP session and `HiveMessageBusClient`, so it runs
  without a live Meta app or a live hub — that also means it cannot catch a
  real handshake hang or a real Cloud API break; treat it as a shape/wiring
  check, not a live-behaviour guarantee.
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is
  a bug to FIX at the source, not to work around with a pin downgrade.

## Repo-specific rules

- **Composition, not inheritance.** `HiveMindWhatsappBridge` builds (or
  accepts an injected) `HiveMessageBusClient` in `__init__` but does **not**
  connect it there — the client is only ever connected once, in
  `connect_hivemind()`. Never add a second call to `connect()` or
  `run_forever()` — `connect()` already starts and owns the reconnect worker
  thread and blocks until the handshake completes.
- **`connect_hivemind()` must bound `handshake_max_retries`.** The
  `hivemind-bus-client` floor is `>=1.0.13a1`; that client's own default for
  `handshake_max_retries` is `None`, meaning retry forever. `connect_hivemind()`
  currently calls `self.client.connect(site_id=self.site_id)` without an
  explicit bound, so a stalled or unreachable hub (down, wrong password) hangs
  this bridge indefinitely instead of failing fast. This is a standing defect,
  not a documented trade-off: fixing it means passing an explicit finite
  `handshake_max_retries` (exposed as a constructor parameter so operators can
  tune it), not merely noting the gap.
- **The hub owns ACL, not this bridge.** A freshly registered HiveMind client
  is denied every message type until an admin runs `hivemind-core allow-msg
  recognizer_loop:utterance <client_id>` (and usually `speak`). This bridge has
  no way to grant itself permissions and must not try to work around a denial
  locally — a silently dropped message on the hub side is the hub doing its
  job, not a bug here.
- **Rejected credentials must fail fast.** Once `handshake_max_retries` is
  bounded (see above), a wrong access key/password must surface as a clean
  failure instead of a bridge that spins forever looking connected. Do not add
  retry/backoff logic on top of `connect()` that defeats this.
- **Nothing is forwarded before the handshake completes.** `handle_webhook`
  checks `self._connected` and drops (with a log warning) any WhatsApp message
  that arrives before `connect_hivemind()` has finished — forwarding earlier
  would get the connection killed by the hub instead of just failing the one
  message. Preserve this guard in any rework of the webhook path.
- **Return upstream responses verbatim.** `handle_speak()` forwards
  `message.data["utterance"]` to WhatsApp unmodified; do not reformat,
  truncate, or add bridge-specific decoration to hub-authored text. The one
  exception is the fixed fallback line on `hive.complete_intent_failure`,
  which is bridge-authored by design because the hub sent no utterance to
  relay.
- **No async/thread bridging needed here, on purpose.** `send_message()` is a
  plain blocking `requests` POST called synchronously from whichever thread
  invoked it (the HiveMind bus's own worker thread for `handle_speak`); it
  must stay synchronous. If a future change makes this bridge `async`-aware
  (e.g. an async HTTP client), any call from the bus thread into the FastAPI
  event loop needs `asyncio.run_coroutine_threadsafe` — a direct `await` from
  a non-loop thread will raise or silently no-op depending on timing.
